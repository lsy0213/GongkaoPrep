# 微服务架构
- 微服务的特点
  - 把单体应用拆成一组小的、自治的服务，每个服务围绕业务能力构建
  - 独立开发、独立部署、独立扩展，可以用不同的技术栈
  - 每个服务独立数据库（去中心化数据管理）
- 微服务的核心组件
  - 服务注册与发现：服务启动时注册，调用方从注册中心获取地址
  - API 网关：统一入口：路由、鉴权、限流、协议转换、聚合
  - 配置中心：集中管理配置，动态刷新；Nacos、Apollo等
  - 熔断 / 降级：下游故障时快速失败，防止雪崩
  - 负载均衡：客户端负载均衡；Ribbon、LoadBalancer
  - 链路追踪：追踪一个请求经过的所有服务；SkyWalking、Zipkin、Jaeger
  - 服务间调用：声明式 HTTP 客户端 / RPC；OpenFeign、Dubbo、gRPC
- 服务拆分原则
  - 按业务能力或领域驱动设计 DDD 的限界上下文拆分
  - 单一职责、高内聚低耦合
  - 避免过度拆分（服务太多运维成本高、调用链长）
  - 考虑团队结构（康威定律：系统结构反映组织的沟通结构）
- 微服务带来的问题与对策
  - 分布式事务：Saga、TCC、可靠消息最终一致（见数据库第 8 课）
  - 服务调用链长、故障传播：熔断、降级、限流、超时重试
  - 运维复杂：容器化 + Kubernetes、自动化部署、集中日志（ELK）等
  - 问题定位难：链路追踪、集中日志
  - 接口版本兼容：API 版本管理、契约测试
  - 数据一致性和查询：CQRS、事件驱动、数据冗余
  - 服务网格 Service Mesh
- 记忆要点
  - 微服务的核心特点：小而自治、独立部署、独立数据库、轻量通信
  - 服务注册中心举例：Eureka、Nacos、Consul
  - API 网关的功能：路由、鉴权、限流、协议转换、聚合
  - 熔断的作用：下游故障时快速失败，防止雪崩
  - 链路追踪工具：SkyWalking、Zipkin、Jaeger
  - 服务拆分的依据：业务能力或 DDD 的限界上下文
