Web、微服务与云原生题是近几年**出现频率最高**的选做题。只要掌握一套“高并发、高可用”的组件清单，大多数问题都能答。

## 一、组件清单（答题素材）

| 目的 | 组件 / 手段 |
|---|---|
| 接入与负载 | DNS、CDN、**Nginx / LVS 负载均衡**、**API 网关** |
| 服务治理 | **注册中心**（Nacos、Eureka）、**配置中心**、**熔断限流**（Sentinel）、链路追踪 |
| 性能 | **Redis 缓存**、本地缓存、静态化、异步、**消息队列**（Kafka、RabbitMQ） |
| 数据 | **读写分离**、**分库分表**、Elasticsearch 搜索、MongoDB |
| 可用性 | 集群、主备、多活、熔断降级、限流、健康检查、自动扩缩容 |
| 部署运维 | **Docker + Kubernetes**、CI/CD、灰度发布、Prometheus 监控、ELK 日志 |

## 二、高频问法

| 问法 | 答案方向 |
|---|---|
| 单体改微服务的拆分原则 | 业务能力 / DDD 限界上下文、单一职责、高内聚低耦合、避免过度拆分 |
| 微服务带来的问题 | 分布式事务、调用链长、运维复杂、数据一致性、测试困难 |
| API 网关的作用 | 统一入口、路由、鉴权、限流、协议转换、聚合 |
| 消息队列的作用 | 异步、解耦、削峰 |
| 分布式事务方案 | 2PC、TCC、Saga、本地消息表 / 可靠消息 |
| 会话管理 | Session 集中存储（Redis）、JWT 无状态令牌 |
| 容器 vs 虚拟机 | 轻量、秒级启动、共享内核、隔离性较弱 |
| Serverless 的优缺点 | 免运维、按量付费、弹性；冷启动、厂商锁定、调试难 |

:::write 微服务改造 | 400 | 12
某在线票务系统采用单体架构，热门演出开票时系统崩溃，且每次发布都要整体停机。拟改造为微服务架构，请说明：(1) 如何拆分服务；(2) 如何应对开票时的高并发；(3) 如何实现不停机发布。
--- 要点
按业务拆分为用户、演出、库存（座位）、订单、支付等服务
每个服务独立数据库，独立部署
CDN 和页面静态化，网关限流
Redis 预扣库存，消息队列异步生成订单（削峰）
熔断降级保护核心链路
Kubernetes 滚动更新或灰度（金丝雀）发布
--- 参考答案
(1) 按业务能力拆分为**用户、演出、座位库存、订单、支付**等服务，各自独立数据库、独立部署，通过注册中心发现，网关统一入口。(2) 演出页**静态化 + CDN**；网关**限流**、验证码分流；座位库存放 **Redis 预扣**，扣减成功后写**消息队列**异步生成订单；非核心功能**降级**，下游故障**熔断**。(3) 服务容器化部署在 **Kubernetes**，采用**滚动更新**或**灰度发布**，配合健康检查和快速回滚，实现不停机发布。
:::

:::cards 记忆卡
消息队列的三大作用 :: 异步、解耦、削峰
API 网关的作用 :: 统一入口、路由、鉴权、限流、协议转换
微服务拆分依据 :: 业务能力或 DDD 限界上下文
秒杀防超卖 :: Redis 原子预扣库存，消息队列异步下单
不停机发布 :: 滚动更新、灰度发布、蓝绿发布
JWT :: 无状态令牌，服务端不保存会话
:::
