上一课认识了每种风格，这一课学“**怎么选**”：案例分析第一题经常给两个候选方案，让你从质量属性的角度对比并选择。

## 一、答题模板

:::flow 选择架构风格的步骤
识别关键需求 :: 从题干找功能特点（批处理？交互？规则多变？）和质量属性（性能、可修改性、可扩展性）
列出候选风格 :: 一般题目已给出 2 个候选方案
逐项对比 :: 按质量属性画对比表：每个风格在该属性上是优还是劣
给出结论 :: 选择更合适的风格，并用题目中的关键需求说明理由
:::

## 二、常考的对比

| 场景 | 方案一 | 方案二 | 推荐与理由 |
|---|---|---|---|
| 编译器 / IDE | 管道—过滤器 | **数据共享（仓库）** | IDE 需要语法树被编辑器、调试器、重构等工具共享，选仓库 |
| 机器人 / 自动驾驶控制 | 闭环控制 | 分层 / 事件驱动 | 环境简单可预测选**闭环**；环境复杂多变、多种任务协调选**分层 + 事件** |
| 规则多变的业务系统 | 面向对象（规则写死在代码里） | **基于规则 / 解释器** | 规则可以由用户配置，不改代码 |
| 集成开发环境的工具协作 | 主程序 / 子程序 | **隐式调用（事件）** | 工具之间松耦合，新增工具不用修改其他工具 |
| 信号处理、语音识别 | 管道—过滤器 | **黑板** | 没有确定的处理顺序，需要多个知识源协同 |

## 三、主要风格的优劣速查

| 风格 | 优点 | 缺点 |
|---|---|---|
| 管道—过滤器 | 简单、**易复用**、**支持并发**、易维护扩展 | 不适合交互，数据格式要统一，性能损耗 |
| 层次结构 | 支持抽象、**易替换某层**、复用性好 | 性能损失，不是所有系统都容易分层 |
| 事件驱动 | **松耦合**、易扩展、复用 | 构件**放弃了对计算的控制**，难测试、难推理 |
| 仓库 / 黑板 | 数据共享方便，知识源可扩展 | 共享数据结构修改困难，控制策略复杂 |
| 解释器 / 规则 | **灵活**，可动态修改 | **效率低**，测试困难 |
| 闭环控制 | 简单、实时、对扰动有反馈 | 只适合简单、可预测的环境 |

:::example 案例题示范（2019 年风格）
某公司开发机器人控制软件，候选方案：A 采用闭环控制风格，B 采用分层架构。机器人要在复杂、不可预测的环境中执行多种任务。选哪个？
--- 分析需求
关键需求：环境复杂、不可预测；任务多样，需要规划、感知、执行多个层次的协调
--- 对比
闭环控制：结构简单、实时性好，但只能处理简单可预测的情况，难以支持多任务协调；分层架构：把感知、规划、控制分层，每层职责清晰，可以替换和扩展，能应对复杂情况
--- 结论
选 **B 分层架构**（也可以说分层 + 事件驱动的混合）。
:::

:::quiz 随堂测验
集成开发环境中，编辑器、编译器、调试器需要共享语法树和符号表，最适合的风格是：
A. 管道—过滤器
B. 数据共享（仓库）
C. 批处理序列
D. 闭环控制
答案：B
---
事件驱动风格的主要缺点是：
A. 构件之间紧耦合
B. 构件放弃了对计算执行顺序的控制
C. 不支持复用
D. 无法扩展
答案：B
:::

:::cards 记忆卡
选择风格的步骤 :: 识别关键需求、列出候选、按质量属性对比、给出结论
管道—过滤器的优点 :: 简单、易复用、支持并发、易扩展
事件驱动的缺点 :: 构件放弃了计算的控制，难测试
解释器风格的缺点 :: 效率低
闭环控制的局限 :: 只适合简单、可预测的环境
复杂环境中的机器人控制 :: 分层架构或分层加事件驱动
